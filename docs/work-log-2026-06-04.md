## 1. Angel One Broker Integration Fix

### Problem
Angel One credentials were added to `.env` but the SmartAPI library's `setAccessToken()` prepends "Bearer " to whatever string it receives, then the header-building code prepends "Bearer " again. The resulting `Authorization: Bearer Bearer <token>` header caused every holdings fetch to return `"Invalid Token"`.

### Fix — `mis-portal/equity/brokers/angel_one.py`
```python
# Strip the "Bearer " prefix that SmartAPI includes in jwtToken before
# passing to setAccessToken(), which adds its own prefix.
access_token = resp["data"]["jwtToken"].removeprefix("Bearer ")
```

The TOTP secret in `.env` must be the raw base32 string from app setup — not the rotating 6-digit code.

## 3. Equity Table — Sector-Based Grouping with Broker Badges

### Background
The equity holdings table was grouped by broker (one section per broker). The request was to group by instrument type instead, with broker identity shown inline per stock.

### Sector classification — `mis-portal/equity/equity_sync_worker.py`

New `classify_sector(symbol, isin)` function uses the ISIN prefix as the primary signal (reliable, already in DB; symbol matching would miss renamed funds):

| ISIN prefix | Sector |
|---|---|
| `IN0` | Sovereign Gold Bond |
| `INF` + `GOLD` in symbol | Gold ETF |
| `INF` + `SILVER` in symbol | Silver ETF |
| `INF` (other) | ETF |
| `INE` | Equity |

`sector` field added to `equity_holding` INSERT and `ON CONFLICT DO UPDATE`.

### DB migration
```sql
ALTER TABLE equity_holding ADD COLUMN IF NOT EXISTS sector TEXT;
-- backfill 45 existing rows
UPDATE equity_holding SET sector = CASE
    WHEN LEFT(isin,3) = 'IN0' THEN 'Sovereign Gold Bond'
    WHEN LEFT(isin,3) = 'INF' AND UPPER(symbol) LIKE '%GOLD%' THEN 'Gold ETF'
    WHEN LEFT(isin,3) = 'INF' AND UPPER(symbol) LIKE '%SILVER%' THEN 'Silver ETF'
    WHEN LEFT(isin,3) = 'INF' THEN 'ETF'
    ELSE 'Equity'
END;
```

## 5. Security Audit and Remediation

Full black/red/white/blue hat audit of the running system. Seven findings, all remediated.

### M1 — Stale JWT role claim (`mis-portal/main.py`)

**Risk:** If a user's role is changed in DB (e.g. admin demoted), their existing JWT still carries the old role claim and retains elevated access until the token expires (2h TTL).

**Fix:** Added `_live_role(cursor, email)` helper that re-queries `users.role` from DB on every request. All four endpoints that gate on role (`get_holdings`, `get_transactions`, `get_entities`, `get_overview`, `_resolve_entity`) now call `_live_role()` instead of reading from `payload["role"]`.

```python
def _live_role(cursor, email: str) -> str:
    cursor.execute(
        "SELECT role FROM users WHERE email = %s AND is_active = TRUE",
        (email,),
    )
    row = cursor.fetchone()
    return row["role"] if row else "member"
```

Uses the existing DB connection already opened by each endpoint — no extra connection overhead.

### M2 — Race condition in broker token write (`mis-portal/equity/tokens.py`)

**Risk:** `write_text()` + `chmod()` is not atomic. If a process reads the token file between the two calls, it can read a world-readable (pre-chmod) token file.

**Fix:** Write to `.tmp`, chmod to 600, then atomically `rename()` over the target:

```python
tmp = _TOKENS_FILE.with_suffix(".tmp")
tmp.write_text(json.dumps(data, indent=2))
os.chmod(tmp, 0o600)
tmp.rename(_TOKENS_FILE)
```

### M3 — Playwright `--no-sandbox` (`mis-portal/workers/cams_trigger_worker.py`)

**Assessment:** `cams_trigger_worker.py` runs as `SAdmin` (unprivileged user, SAdmin's crontab). `--no-sandbox` is dangerous when Chromium runs as root because a renderer exploit then has unrestricted system access. Since the process is already unprivileged, the risk is substantially lower. No code change required; documented as accepted risk.

### M4 — PAN numbers and CAS emails in `.env`

**Risk:** `.env` is a flat file committed to git history and readable by any process with filesystem access. PAN numbers are high-value PII; CAS emails are account identifiers.

**Fix:**
- Added `pan_number VARCHAR(10)` to `pan_group` table; populated all 6 values
- Added `cas_email VARCHAR(255)` to `entity` table; populated all 6 values
- `cas_automation_worker.py` now calls `_entity_configs()` which loads both from DB via a single JOIN query
- Removed all `ENTITY_*_PAN` and `ENTITY_*_EMAIL` lines from `.env`

```sql
ALTER TABLE pan_group ADD COLUMN IF NOT EXISTS pan_number VARCHAR(10);
ALTER TABLE entity    ADD COLUMN IF NOT EXISTS cas_email  VARCHAR(255);
```

```python
def _entity_configs() -> list[EntityConfig]:
    # loads code, email, pan from DB — no env vars needed
    cur.execute("""
        SELECT e.entity_name AS code, e.cas_email AS email, pg.pan_number AS pan
        FROM   entity e
        JOIN   pan_group pg ON pg.id = e.pan_group_id
        WHERE  e.cas_email IS NOT NULL AND pg.pan_number IS NOT NULL
        ORDER  BY e.id
    """)
```

### M5 — Nginx server header exposure

**Fix:** Added `proxy_hide_header Server`, `proxy_hide_header X-Powered-By`, and `add_header Server "" always` at the server block level in nginx config. After `nginx -s reload`, the `Server` response header shows `cloudflare` (Cloudflare's own header, which is expected and does not reveal origin stack).

### M6 — PII in worker log lines

**Risk:** CAS worker logs were writing investor names, emails, and PAN prefixes at INFO level. Log files are world-readable (`-rw-r--r--`).

**Fixes:**
- `cas_parser_worker.py`: removed `logger.info(f"Investor: {data.investor_info.name}")` and email line; replaced with `logger.info("CAS PDF parsed successfully")`
- `cas_automation_worker.py`: removed entity email from trigger separator line; PAN prefix removed from order log
- `cams_trigger_worker.py`: removed PAN and filename from screenshot log lines

### M7 — Screenshot file permissions

**Risk:** Screenshots taken by `cams_trigger_worker` captured form fields including PAN, email, and PDF password. Old screenshots in `~/.cams-screenshots/` had permissions `664` (group and world-readable).

**Fix:**
- `_save_screenshot()` now calls `os.chmod(path, 0o600)` after every `page.screenshot()`
- Applied `chmod 600` to all 21 existing screenshots retroactively
- Directory `~/.cams-screenshots/` already had `700` permissions

## 6. Log File Ownership Fix

**Problem identified:** `/var/log/mis-portal-cas-auto.log` was owned by `cams-worker:cams-worker` (set during M3 investigation). `cas_automation_worker.py` runs as `SAdmin` (from SAdmin's crontab). SAdmin cannot write to a `cams-worker`-owned 640 file — this would silently crash the CAS automation at startup, preventing all 6 entities from being triggered (same failure mode as the Jun 1 complete miss).

**Fix:**
```bash
sudo chown SAdmin:SAdmin /var/log/mis-portal-cas-auto.log
sudo chown SAdmin:SAdmin /var/log/mis-portal-cas-worker.log
```
